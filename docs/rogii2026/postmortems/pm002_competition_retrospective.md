# pm002: ROGII 2026 コンペ全体のふりかえり（4365位 / 6125チーム）

作成日: 2026-08-21（コンペ終了後）。対象期間: 2026-05-05 〜 2026-08-05。
上位解法の要約は `research/top_solutions.md`。

## 何を期待していたか

`strategy.md` の目標: 「公開水準 8.07 を有意に下回る」「7 を切れたらメダル圏視野、6 切りで上位安定」。
H9 ロードマップ（exp005〜exp012）で OOF 14.28 → 10.4 相当まで詰める計画。

## 何が起きたか

| 指標 | 結果 |
|---|---|
| 最終順位 | **4365位 / 6125チーム**（private 12.693 / public 12.959） |
| 提出回数 | **1回**（exp001、締切の約 2 ヶ月前） |
| 1st / 2nd / 3rd | 5.639 / 5.802 / 5.836 |
| 49位のスコア | 6.999 |
| flat anchor（null model） | 約 15.9 |
| 最終活動 | git log は 2026-07-09 で停止。exp006 の記録が 07-17。**残り 3 週間の活動記録なし** |

- 全実験を通じて OOF は exp001 の 14.28 が最良のまま。exp002 (14.66) / exp004 (14.32) / exp004b (14.30) / exp006 (ABANDONED) は**すべて改善ゼロまたは悪化**
- 実質的な成果は「null model から −3.2」。上位との差は約 7 ft

## なぜ起きたか（5 Why）

### Why 1: なぜ 12.7 で終わったか？
→ 提出可能な最良モデルが exp001（LightGBM 残差回帰）のまま、5〜6月に確立したベースラインから 2 ヶ月間 1 度も更新されなかったから。

### Why 2: なぜ 2 ヶ月間ベースラインが更新されなかったか？
→ 4 実験連続（exp002, 004, 004b, 006）で改善ゼロだったから。そしてその 4 実験はすべて
**「手作りの GR 整列アルゴリズム（beam / NCC / DTW）でパスを 1 本推定し、その要約統計を LightGBM の特徴量に入れる」という同一の定式化の枝**だった。幹が間違っていたので、どの枝を試しても実らなかった。

### Why 3: なぜその定式化が間違っていたと気づけなかったか？
→ 2nd place が明記している通り、この問題の posterior は **多峰**（typewell GR は似た縞が繰り返す）。
単一パスに畳んだ時点でモード平均に崩壊し、少数ウェルで大外れする。pm001 で観測した
「大半のウェルは 11.85ft だが 2fd68f7b が 61.9ft」はこの構造的性質そのものだった。
しかし pm001 の 5 Why は 5 段すべて**実装レベルの why**（「anchor 再制約が無い」「gate が平均値だけ」）に留まり、
**「そもそも 1 本のパスに畳むこと自体が誤りではないか」という定式化レベルの why に到達しなかった**。
結果、pm001 の処方箋は「もっと良い整列アルゴリズムを探す」となり、exp006/007/008 という同じ幹の枝が量産された。

### Why 4: なぜ定式化レベルの選択肢（2D 確率場 + CNN）が視野に入らなかったか？
→ **Discussion の調査を実質的に一度も行わなかったから。**
`research/discussions.md` は最終更新までテンプレートのままで、実質的な記載は 1 行、しかもその内容は
「本文未読（WebFetch が Kaggle の SPA を取得できずタイトルのみ返却）」。
実際には hengck23 の 62 upvote スレッド（2026-05 投稿 = リサーチ開始より前から存在）に、
上位 2 チームが実際に使った中核が全部書かれていた:
- 2D heatmap → CNN → MDN による multi-trajectory prediction（**2nd place が明示的に出発点と述べている**）
- 動く実装 notebook 2 本（cnn-mtp-example / cnn-sdf-example）
- dz annotation leak（ANCC は約15制御点の区分線形 = 2nd place の恒等式 `dTVT = dz_layer − dz`）
- `cumsum(−dz − offset)` だけで RMSE 7.7（当時の公開最高 8.07 より良い）
- 地層面 kriging で validation RMSE ≈ 11（1st place の XY 近傍単体 11.4 とほぼ同じ）
- host のヒント（PS 以前の lateral GR を GR 相関に使え = 2nd の x6 チャネル）

WebFetch が失敗した時点で「次回セッションでブラウザから確認することを推奨」と書いて放置し、
2 ヶ月間その TODO が回収されなかった。**今回のふりかえりでは同じページをブラウザで 30 秒で取得できた。**

### Why 5: なぜ「Discussion 未読」が 2 ヶ月放置されたか？
→ CLAUDE.md の Phase 1 に「`research/discussions.md` に重要 Discussion の要点を記録」と書いてあるが、
**完了条件が定義されておらず、Phase 2 以降に進むゲートになっていなかった**。
一方で `experiments.md` の更新義務や gate 基準は厳密に運用されていた。
つまり「実験ループの規律」だけが強く、「情報収集の規律」に強制力が無かった。
結果、情報源が pilkwang / boristown の公開 Notebook 2 本だけになり、しかもその 2 本は
自分自身が「same-well shortcut で汚染されている」と分析した notebook だった。
**汚染されていると分かっているソースが、唯一の羅針盤になっていた。**

## 上位との具体的な差分

| 論点 | 上位（1st / 2nd 共通） | 自分 |
|---|---|---|
| 定式化 | 2D 整列（typewell level × MD）の**確率場**推定 | 行ごとの残差回帰（GBDT） |
| 多峰性 | 確率分布として保持し、DP で期待値デコード | 手作り探索で単一パスに畳んで特徴量化 |
| モデル | CNN（U-Net + ConvNeXt / EfficientNet + FPN anchor） | LightGBM のみ。NN は最後まで「未着手候補」 |
| 学習データ | `GR = f(TVT)` 生成モデルで合成データを大量生成 + 重い aug | 実データ 773 well のみ、aug なし |
| trajectory の使い方 | `z_diff` / XY近傍最小二乗 / 恒等式 `dTVT = dz_layer − dz` | `-Z` と累積変位を素の特徴として投入 |
| 検証 | GroupKFold OOF + 少数ウェル支配に頑健な受け入れ検定 | GroupKFold OOF（設計は正しい） |
| 計算資源 | 単一 GPU 10 時間程度（特別な資源は不要） | CPU / GBDT のみ |
| 提出 | 45〜433 entries | **1 entry** |

## 良かった点（次も続けるべきこと）

- **リーク分析は正しかった**。boristown notebook の same-well shortcut（`if wid in train_wells: hw_te['TVT_input'] = hw_tr['TVT_input']`）を実コードから特定し、公開LB 7.159 を疑って GroupKFold OOF を信じる方針にしたのは上位と同じ判断。実際 private は大荒れ（1st +30位、11位 +193、15位 +1561、30位 +1901）で、public を追った参加者は落ちている
- **pm001 の訂正**（自分の初版の「累積 drift」結論を実 tail データで反証し、書き直した）は誠実で質が高い
- GroupKFold(well_id) の徹底、gate 基準を数値で事前に置く運用、実験ドキュメントの粒度

問題は「正しい検証設計を作ったが、その上で走らせるモデルが弱すぎた」こと。

## 悪かった点（構造的な問題）

1. **情報収集の規律が無かった**（Why 4/5）。最大かつ単独で順位を説明できる要因
2. **同一定式化での連続失敗に対する脱出条件が無かった**。4 連続ゼロ改善でも幹を疑わなかった
3. **アーキテクチャ族を 1 つしか走らせなかった**。`strategy.md` は H5（1D-CNN/Transformer）を
   「効果は出るが投資対効果は他より下」と優先度 5 位に置いたが、**この判断に根拠データが無い**。
   CLAUDE.md 自身の「推測ではなくデータに基づく判断」に反している。実際には上位2チームとも CNN が本体で、
   必要な計算資源は単一 GPU 10 時間程度だった
4. **gate 基準が「勝てるか」ではなく「マシか」を測っていた**。flat anchor 12.8ft を延々と基準にし続けたが、
   上位は 5.6。null model に勝つのは必要条件であって、メダル圏への道筋とは無関係だった
5. **残り時間と計画の粒度が整合していなかった**。7/17 時点で残り 19 日に対し exp005〜exp012 の 8 段階計画
   （1 段階あたり 2 日強）を立て、1 段目の exp006 で不合格になった時点で計画全体が破綻した
6. **提出が 1 回**。CV-LB 相関を測るという自分の計画も 1 点しか取れず「相関未確定」のまま終わった
7. **終盤 3 週間の活動が消失**。締切前の最も価値が高い期間に記録が無い

## 次回どうするか（CLAUDE.md への反映候補）

1. **Phase 1 の完了条件を「Discussion upvote 上位 10 スレッドの本文を読み、要約を書いた」まで含めて明文化し、
   これを満たすまで Phase 3（仮説検証ループ）に入らない**。特に host のコメントと、コンペ中に手法を晒す
   高レート参加者のスレッドは最優先。**WebFetch が Kaggle 等の SPA で失敗したら即ブラウザ（claude-in-chrome）に切り替える**。
   「未読」の TODO を次セッションに送ってはならない
2. **`expXXX.md` に「失敗の層」欄を追加**（実装レベル / ハイパラレベル / **定式化レベル**）。
   **同一定式化で 2 連続ゼロ改善したら、次の 1 実験は必ず別定式化に充てる**（枝の深掘り禁止）
3. **ベースラインのアーキテクチャ族を最低 2 つ並走させる**（GBDT 系と NN 系）。
   片方だけで 3 実験以上連続は禁止。「投資対効果が低い」という判断は、最低 1 回動かしてから下す
4. **gate 基準は null model ではなく「想定メダル圏スコアへの残距離」で置く**。
   「flat anchor に勝つ」は通過条件であって目標ではない
5. **`strategy.md` に常に「残り日数 / 1実験の所要日数 = 残り実験可能数」を書き、計画の段数がそれを超えたら計画を切る**
6. **提出は週 1 回以上を下限にする**。CV-LB 相関の測定にも、終盤の submission デバッグにも必要
7. **多峰性のあるマッチング問題では、単一の最良パスに畳まず分布として扱えないかを最初に検討する**
   （このコンペのドメイン固有の学び。整列・対応付け・retrieval 系のタスク全般に効く）
